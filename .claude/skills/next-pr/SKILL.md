# 積まれたPRを1本ずつ片付ける

## このスキルの単位

**1回の起動 = PR 1本を、マージまたは「人間に聞く」まで持っていく。**

複数のPRをまたいで進めない。1本終えたら報告して終わる。`/loop` から呼ばれている場合、
次の起動が次の1本を担当する。この粒度を守ることで、途中で中断されても状態が中途半端にならない。

## 0. 対象を1本選ぶ

```bash
gh repo view --json defaultBranchRef --jq .defaultBranchRef.name   # 以下 <base> と書く
gh pr list --state open --json number,title,headRefName,baseRefName \
  --jq '.[] | "#\(.number) \(.headRefName) -> \(.baseRefName) | \(.title)"'
```

**必ずスタックの一番下から。** 上のPRから触ると、下がマージされた瞬間に差分が崩れる。
一番下とは、base が `<base>` のPR。それが無ければ、base ブランチが既にマージ済みのPR
(= base を `<base>` に付け替えられるPR)。PR番号順が最下層とは限らないので、base を見て判断する。

開いているPRが1本も無ければ、**そこで終わり**。ループを止めて(`ScheduleWakeup` の `stop: true`)、
全部片付いたことを報告する。止めないと同じ確認を延々と繰り返す。

base が既定ブランチ以外のまま残っていたら、先に付け替える:

```bash
gh pr edit <N> --base <base>
```

## 1. 最新の既定ブランチを取り込む

**これを最初にやる。** 積まれたPRは古い状態の上に乗っている。取り込まずにレビューすると、
既に別のPRで直った問題を再指摘したり、逆に既定ブランチ側の変更との衝突を見逃す。

```bash
git fetch origin --prune
git checkout <headRefName>
git merge origin/<base> --no-edit
```

自動マージできれば進む。コンフリクトが機械的なもの(import の並び、隣接行)なら解決して進む。
どちらの意図を採るかの判断が要るコンフリクトは、**人間に聞く**(→「止まる条件」)。

取り込んだ結果が壊れていないかを、この時点で一度確認する(→ 3.)。

## 2. そのリポジトリの流儀を掴む

初めて触るリポジトリなら、これを先に見ておく。後の工程で毎回迷わなくなる。

- **コミットメッセージ**: `git log --format='%s%n%n%b' -20`。件名の言語・形式(命令形の英語か、
  `chore:` のような prefix か)と、本文で何を書く文化か(「何を」だけか、「なぜ」まで書くか)
- **マージ方式**: `gh pr list --state merged --limit 10 --json title` と `git log --merges -5`。
  マージコミットか squash か
- **検証手段**: `package.json` の scripts、`Makefile`、CI 設定(`.github/workflows/`)。
  テストがあるか、無いなら何で代替しているか
- **プロジェクト側の指示**: `CLAUDE.md`、`.claude/skills/`。リポジトリ固有の検証スクリプトや
  規約が置かれていることがある。**あれば必ず読んで使う** — 手で組み直すより速く、正確

## 3. `/review` → 修正 → コミット を、重大な指摘が尽きるまで

**`/code-review` は使えない。** 利用者本人がタイプしたときだけ動くコマンドで
(`disable-model-invocation`)、スキルの中からモデルが起動すると弾かれる。
別の手段で同じことをやり直すのも禁じられている。ここでは PR を対象にする `/review` を使う。
手元の未コミット分は `/review` の視界に入らないので、**巡ごとに必ずコミットして push してから**
次の `/review` を回す。push しないと、直した内容がレビュー対象にならない。

どうしても `/code-review` の指摘が要る場面(PR にする前の差分を見たい等)は、
利用者に「`/code-review` を打ってほしい」と頼んで止まる(→「止まる条件」)。

1. `/review <N>` を実行する
2. 指摘を読む。**直すものと直さないものを自分で判断する** — 指摘は仮説であって命令ではない。
   誤検知だと判断したら直さず、なぜそう判断したかを述べる
3. 直したらコミットして push する(1巡 = 1コミット。巡ごとに切ると、後から
   「何がどの指摘への対応か」が追える。push は次の `/review` に変更を見せるために要る)
4. 指摘が無くなるまで 1 に戻る

**自分の修正が次の巡の対象になる。** これがこのループの肝で、1巡で終わらせてはいけない理由でもある。
実例: 「重複したロジックを共有モジュールに切り出す」修正が、次の巡で
「その共有化でスクリプトの読み込み方が変わった、実際に動かして確かめたか」という検討を生んだ。
修正は新しい面を作る。作った面をもう一度見る。

**収束しない場合**: 5巡しても新しい重大指摘が出続けるなら、PRの設計自体に問題がある可能性が高い。
巡を重ねるのをやめて人間に聞く。

**「重大」の線引き**: 実際に誤動作する経路があるものは直す。命名や好みは直さない。
その中間 — 「今は動くが、次に触る人が踏む」もの(重複した判定ロジック、
未検証の前提をドキュメントに断定で書いている、等) — は、直すコストが小さいなら直す。
判断に迷ったら直す側に倒す。このスキルの目的は、レビューを通すことではなくPRを安心して閉じることなので。

## 4. 実際に動くことを確かめる

2. で見つけた検証手段を回す。テストがあれば走らせる。無いリポジトリでは、
最低でも構文チェック相当(`node --check`、`tsc --noEmit`、`ruby -c`、ビルド)は通す。

**構文チェックは構文しか見ない。振る舞いを変えたなら、振る舞いを確かめる。**
プロジェクト側に検証用のスクリプトやスキルがあればそれを使う。無くて、かつ手元で動かせる
形にできるなら(ローカルサーバ、スタブ、CLI の直接実行)、その足場を組んで確かめる。
その足場が次のPRでも使えそうなら、プロジェクト側の `.claude/skills/` に残すことを提案する。

**自分では確かめられない種類の変更**もある。実行環境そのものが要るもの(ブラウザ拡張の
content script、OS権限、外部サービス連携)や、権限・設定を**削る**変更がそれにあたる。
コードを読むだけでは「削って壊れない」ことは分からない。そういうPRは、
「たぶん大丈夫」でマージせず人間に頼む(→「止まる条件」)。

## 5. マージする

ここまでで人間に聞くことが無ければ、マージしてよい。

```bash
git push origin <headRefName>
gh pr merge <N> --merge     # 2. で確かめた方式に合わせる(--squash のリポジトリもある)
```

**スタックが残っているうちは head ブランチを消さない。** 上に積まれたPRの base になっているため。
代わりに、次のPRの base を明示的に付け替える:

```bash
gh pr edit <次のN> --base <base>
```

マージ後、何をしたか(何巡回って何を直したか、何を確認したか、残りは何本か)を報告して終わる。

## 止まる条件 — 人間に聞くべきとき

以下に当たったら、**その場で止めてループも止め**(`ScheduleWakeup` の `stop: true`)、質問する。
止めずに聞くと、返事を待つ間にループが次の起動をかけて同じ所を踏む。

- **仕様の判断が要る指摘**。「この挙動は許容するのか、直すのか」がプロダクトの決めごとになるとき。
  ただし、影響範囲が限定的で、判断とその理由をドキュメントに残せるなら、自分で決めて進めてよい
- **意図の判断が要るコンフリクト**
- **5巡しても重大指摘が収束しない**
- **PRの説明と実装が食い違っている**
- **実行環境が要って自分では確かめられない変更**、特に権限・設定を削るもの
- **CI が落ちている**、または落ちている理由が分からない
- **`/code-review` の指摘が要る**と判断したとき。モデルからは起動できないので、依頼して待つ

逆に、これらは自分で決めて進めてよい: コードの直し方、コミットの切り方、ドキュメントの書き方、
指摘を誤検知として退けること、機械的なコンフリクト解決。

## 詰まったとき

- コマンドが「信頼されていない」系のエラーで落ちるなら、バージョン管理ツール側の許可を疑う
  (`mise trust`、`direnv allow`)。worktree や clone 直後によく起きる
- `gh pr merge` が無言で終わることがある。`gh pr view <N> --json state,mergedAt` で結果を確かめる
